# Dayflow HRMS — Database Design

Backend: PostgreSQL (Odoo's only supported DB — not a separate choice).
Schema is generated by the Odoo ORM from Python model definitions; no
hand-written DDL or manual migrations.

## Design principle

Extend Odoo's existing HR schema. Only add tables where no Odoo equivalent
exists. Result: **2 new tables, 7 extended/reused tables, 0 redundant
tables.**

## Entities

### Reused / extended (Odoo built-in)

- `res.users` — authentication identity (email, password hash, active flag).
  Not duplicated by a custom table.
- `hr.employee` — HR record: name, department_id (FK), job_id (FK),
  parent_id (FK, self-referencing = manager), user_id (FK to res.users),
  address, phone, image (profile picture).
- `hr.department` — id, name, manager_id.
- `hr.job` — id, name, department_id.
- `hr.attendance` — id, employee_id (FK), check_in (datetime),
  check_out (datetime). No stored status column (see below).
- `hr.leave` — id, employee_id (FK), holiday_status_id (FK to
  hr.leave.type), date_from, date_to, state (draft/confirm/validate/refuse),
  first_approver_id (FK), private_name (remarks).
- `hr.leave.type` — id, name, requires_allocation (paid/unpaid distinction).

### New custom tables

**hrms.salary.structure**

| Field | Type | Constraint |
|---|---|---|
| id | serial | PK |
| employee_id | int | FK → hr.employee, required |
| basic_salary | numeric | required, > 0 |
| allowances | numeric | default 0 |
| deductions | numeric | default 0 |
| effective_from | date | required |
| effective_to | date | nullable (null = currently active) |

Business rule enforced in Python (`create`/`write`), not raw SQL: only one
row per employee may have `effective_to = null` at a time. Creating a new
structure for an employee auto-closes the previous one
(`effective_to = new.effective_from - 1 day`).

**hrms.payslip**

| Field | Type | Constraint |
|---|---|---|
| id | serial | PK |
| employee_id | int | FK → hr.employee, required |
| salary_structure_id | int | FK → hrms.salary.structure, required |
| month | int | required, 1-12 |
| year | int | required |
| basic_salary | numeric | snapshot, copied at generation |
| allowances | numeric | snapshot |
| deductions | numeric | snapshot |
| gross_salary | numeric | computed + stored = basic + allowances |
| net_salary | numeric | computed + stored = gross - deductions |
| generated_at | datetime | auto |

SQL constraint: `unique(employee_id, month, year)` — one payslip per
employee per pay period.

## Relationships

```
hr.department     1 ─── N   hr.employee
hr.job             1 ─── N   hr.employee
hr.employee        1 ─── 1   res.users
hr.employee        1 ─── N   hr.attendance
hr.employee        1 ─── N   hr.leave
hr.leave.type      1 ─── N   hr.leave
res.users (HR)     1 ─── N   hr.leave            (as approver)
hr.employee        1 ─── N   hrms.salary.structure
hr.employee        1 ─── N   hrms.payslip
hrms.salary.structure 1 ─ N   hrms.payslip
```

## Rejected designs (and why)

- **Custom `USER` table with password_hash/role** — rejected. Duplicates
  `res.users`, which already handles auth. Two parallel identity systems
  is a red flag, not a strength, in an Odoo-specific hackathon.
- **Custom `AUDIT_LOG` table** — rejected as a table. Odoo's `mail.thread`
  mixin gives chatter/audit logging on any model for free; no schema cost.
- **`department` as free-text string** — rejected. `hr.department` already
  exists as a real table; using it costs nothing and enables reporting.
- **`job_title` as its own normalized entity** — not needed beyond what
  `hr.job` already provides.
- **Fully normalized salary components** (separate `SALARY_COMPONENT`,
  `SALARY_STRUCTURE_COMPONENT` join table) — overengineering for an
  8-hour build; flat columns (basic/allowances/deductions) cover the
  actual requirement.
- **Stored `status` column on attendance** — rejected. Status is derived
  from check_in/check_out/leave data; storing it risks drift/inconsistency.

## Historical correctness

Payslips snapshot salary values at generation time rather than referencing
`hrms.salary.structure` live. If a salary structure changes after a payslip
is generated, past payslips remain accurate.

## Constraints summary

- `unique(employee_id, date)` — effectively enforced via Odoo's attendance
  validation (no overlapping open check-ins per employee).
- `unique(employee_id, month, year)` on `hrms.payslip`.
- `unique(user_id)` on `hr.employee` — 1:1 with res.users (Odoo default).
- Record rules (not just UI hiding) restrict employees to their own
  attendance / leave / payslip rows — see `permission-matrix.md`.
